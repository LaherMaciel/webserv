You are writing the program that a browser talks to. Everything else in this project is a consequence of that one sentence — and this page is the picture behind it.

01 — the whole project in one exchangeWhat you are actually building

A web server is a program that holds a socket open, waits for someone to send it text, and sends text back. That is genuinely all it is. The difficulty is never one exchange — it is a hundred of them at once, on one thread, without ever freezing.

When you type an address into a browser, the browser opens a TCP connection to your machine and writes some plain, human-readable text into it. Your program reads that text, decides what it means, and writes different text back. If the text you write back is well-formed, the browser renders a page. If it is off by a single byte, the browser shows nothing and tells you nothing.

02 — the bytesWhat a request and a response really look like

There is no magic layer. HTTP is text with a strict shape, and every line ends with carriage-return + line-feed — \r\n, both characters, always.

Here is a real request, exactly as it arrives in your recv() buffer. The → marks are where \r\n sits; they are not visible characters, but they are bytes you must count.

bytes arriving on the connection fd
GET /index.html HTTP/1.1→
Host: localhost:8080→
User-Agent: Mozilla/5.0→
Accept: text/html→
Connection: keep-alive→
→   ← blank line: headers are over

Line one is the request line: method, target, version. Then headers, one per line, Name: value. Then a blank line. For a GET, that blank line is the end of the message — there is nothing after it.

And what you must write back:

bytes you send on the same fd
HTTP/1.1 200 OK→
Content-Type: text/html→
Content-Length: 38→
→
<html><body><h1>Hi</h1></body></html>

Line one is the status line: version, code, reason phrase. Then headers, then a blank line, then the body. Content-Length is a promise: it says the body is exactly that many bytes. Break the promise and the browser hangs waiting for bytes that never come, or cuts your page off mid-tag — with no error message either way.

Try this before you write any code

Run curl -v http://example.com and read what scrolls past. Lines starting with > are what curl sent; < is what came back. That is the entire protocol, visible, in one command. Then run it against nginx on your own machine and compare.

03 — the question that designs your parserHow do you know the message ended?

TCP gives you a stream of bytes with no message boundaries. One recv() may hand you half a request, or two requests stuck together. So: when have you read enough to stop and act?

There are exactly three answers, and which one applies is decided by the headers. If you can state all three before you write the parser, the parser designs itself. If you can't, you will discover them by crashing into them.

Why this matters for CGI later

A CGI script has no concept of chunks — it reads its body from stdin until end-of-file, and it trusts CONTENT_LENGTH. So a chunked request must be un-chunked by you before the script ever sees it. That requirement in the subject is not arbitrary; it falls directly out of case 3 not existing in CGI's world.

04 — the constraint that shapes everythingWhy poll() exists

One process. One thread. A hundred clients. Some of them slow, some of them malicious, one of them a browser that opened a connection and then said nothing at all.

A normal read() on a socket blocks: if no data has arrived, your program stops there, doing nothing, until data comes. With one thread, one silent client freezes every other client on the server. That is why the naive version fails, and it is why the subject bans blocking.

This is a grade-zero rule, not a style preference

One poll() for everything. It must watch readable and writable at the same time. Never read or write a socket or pipe that poll() did not just report ready. Regular disk files are exempt in subject v24.1 — but the older evaluation sheet is stricter, and being stricter costs you nothing.

05 — the heart of the programEach connection is a state machine

This is the idea that turns a thousand special cases into six boxes and a handful of arrows. If you understand one diagram on this page, make it this one.

A connection is not an event, it is a lifecycle. At any moment it is somewhere specific: still collecting the request, working out the answer, pushing bytes out, or finished. "Readable" means something different in each place. When each connection object knows its own state, poll() becomes trivial to act on — you look at the state, and the state tells you what to do.

The eval question this answers

"A connection is halfway through writing a large response and poll() reports it writable again — what do you do?" Answer: continue from the stored offset, send what you can, update the offset. Not restart. Not buffer-and-hope. The state object already knows where it was.

06 — from URL to fileThe config decides everything

The subject hands you a design problem most students have never had: invent a configuration format. nginx is your reference for what a consistent one looks like.

A request arrives with a path. Which file on disk is that? The answer is not string concatenation — it is a lookup through the config, and the subject spells out the exact example: if /kapouet is rooted to /tmp/www, then /kapouet/pouic/toto/pouet must resolve to /tmp/www/pouic/toto/pouet. Notice what happened to the matched prefix: it was replaced, not kept.

07 — the fossilCGI, and what a "backend" actually is

Before frameworks, this was the dynamic web: the server runs a program and sends you whatever it prints. Understanding it is understanding what Django and Node abstracted away.

CGI has no library and no API. The server puts the request into environment variables, pipes the body to the child's standard input, runs an interpreter, and reads the answer from the child's standard output. That is the entire interface, unchanged since 1993.

08 — tomorrow's conversationWhere the work splits in two

Two people, one server. There is essentially one clean seam through this project, and several messy ones. Agreeing the seam is the most valuable thing you can do with Beth before either of you writes code.

The clean seam is between moving bytes and deciding what the bytes mean. One side owns the socket, the poll loop, the connection state machine, and turning raw bytes into a Request object — and turning a Response object back into bytes. The other side owns everything that takes a Request and produces a Response: the config file, route matching, static files, directory listings, uploads, DELETE, CGI.

Bring these to the conversation

What exactly is in Request and Response? Who writes the config parser — it is the biggest single lump on side B. Who owns the Makefile and the directory layout? And which of you writes the first throwaway server that just accepts a connection and replies 200 OK to everything, so there is something real to build against on day one?

09 — before you write anythingThe rules that end an evaluation

Most of these cannot be patched in later. They are consequences of the architecture, which is why they belong in your head before the first line, not after the last.

  • ZEROAny crash, ever. Segfault, uncaught exception, unexpected termination — even out of memory. The grade is 0 and the defence stops.
  • ZEROChecking errno after read / recv / write / send to decide what to do next. Readiness comes from poll(), and only from poll().
  • ZEROMore than one poll(), or a poll that does not watch readable and writable simultaneously.
  • ZEROReading or writing a socket or pipe that poll() did not report ready.
  • ZEROA forbidden function, an external library, or Boost. Also: fork() for anything except CGI, and execve-ing a real web server.
  • FLAGMemory leaks, or a relink on a second make. Both are flags rather than instant zeros, but both are trivially checkable and will be checked.

Two more that are not zeros but decide the grade: every status code must be correct, and the server must survive a siege -b stress run at over 99.5% availability with flat memory and no hanging connections, indefinitely, without a restart.

10 — check yourselfQuestions to answer out loud

Not for the evaluator. For tomorrow — if you can answer these without notes, you can lead the conversation instead of following it.

What are the three ways a request can end?

No body at all (the blank line ends it); Content-Length: N (exactly N bytes follow the blank line); Transfer-Encoding: chunked (sized pieces until a zero-size chunk). The headers decide which — never the return value of recv().

Why can't you just call read() when a client connects?

Because read() blocks until data arrives, and you have one thread. A client that connects and says nothing would freeze every other client. poll() exists so you only ever touch descriptors that are ready right now.

What does accept() actually give you?

A new file descriptor for that one conversation. The listening socket is a factory — it never carries request or response data. Each connection fd has its own buffers and its own state.

You sent 4 KB of a 2 MB response and send() won't take more. Now what?

Stay in WRITING, store the offset, return to the loop and serve other clients. When poll() reports that fd writable again, continue from the offset. Never restart the response, never block waiting.

A CGI script gets no arguments and no request object. Where does it find the method and the body?

The method, query string and content length come from environment variables you set before execve. The body arrives on its standard input through a pipe you created. You put every one of those there yourself.

Why must a chunked body be un-chunked before the CGI sees it?

CGI has no notion of chunking. It reads stdin to end-of-file and trusts CONTENT_LENGTH — and you cannot state a length you haven't finished receiving. So you decode the chunks, count the real total, and hand over a plain body.

Two server blocks on the same port, and a request matching neither name. What happens?

The first block declared for that port answers as the default server. This is exactly the case the evaluation sheet probes with curl --resolve, and the case where "it works in my browser" tells you nothing.
